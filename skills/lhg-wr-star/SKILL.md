# lhg-wr-star：STAR 式事项描述

> 目标：让"本周完成"的每一条都经得起追问"所以呢"。核心纪律：**没有结果的事项不许进周报**——"做了"是过程，"做成什么样"才是结果。
> 适用对象：周报"本周完成"章节、项目复盘、述职材料。
> 前置：事项清单已收齐（lhg-wr-structure 第 4 步第 1 环）。

## 1. 何时使用

- 写"本周完成"的每一条 → 逐条套用
- 用户的原始记录只有过程（"在做 xx"）→ 用第 4 步追问法挖结果
- 审别人的周报 → 用第 5 步质检表

## 2. STAR 四要素（周报版）

| 要素 | 问什么 | 周报里写多少 |
|---|---|---|
| S（背景） | 为什么做这件事 | 一句话，或直接省略（老板知道背景） |
| T（任务） | 目标是什么 | 半句话，常和行动合并 |
| A（行动） | 你具体做了什么 | 一句话，写关键动作，不写流水账 |
| R（结果） | 做成了什么样 | **必须有**：数字、交付物、上线状态三选一 |

**周报里的 STAR 是压缩版**：S/T 经常一句话带过，A 一句话，R 必须量化。完整例子：

```
- 完成支付链路幂等改造并上线：上线 3 天零 P0 故障，
  支付成功率从 97.2% 提升到 99.1%，掉单客诉清零
  （S：掉单客诉上升；T：两周内改造；A：重写幂等+补对账；R：成功率 99.1%）
```

括号里的 S/T/A 是"防追问备注"：老板不问就不展开，问了你答得上来。新手建议先写全，老手可以只写 R。

## 3. 结果的三种写法

1. **数字结果**（最优先）：成功率 97.2%→99.1%、交付 5 个需求、修复 8 个 bug。
2. **交付物结果**：上线了 xx、发布了 xx 文档、通过了 xx 评审（交付物=可验证的存在）。
3. **状态结果**（保底）：联调通过、验收通过、零故障运行 x 天（实在没数字时用，但一周最多 1 条）。

**结果动词库**（审计脚本 STAR-001 就认这些）：完成、上线、交付、修复、提升、增长、下降、发布、通过、解决、降低、新增、优化、落地。写事项时优先用它们开头。

## 4. 过程型记录的追问法

用户原始记录常常是过程型的，按这个顺序追问（最多 2 轮）：

```
原始："在跟进支付改造"
追问1：改造到哪一步了？→ "代码写完了，在联调"
追问2：联调结果？什么时候能上？→ "联调通过，预计周三上线"
成稿："完成支付链路幂等改造并通过联调，预计周三上线"
```

```
原始："开了 3 个需求评审会"
追问1：评审结论？→ "2 个通过，1 个打回"
成稿："完成 3 个需求的评审：2 个通过进入开发，1 个打回补充方案"
```

**追问铁律**：问"结果"，不问"过程"。不要问"怎么做的"，要问"做成什么样了""数字是多少""什么时候交付"。

## 5. 事项质检表

每条事项写完后过一遍：

- [ ] 有结果（数字/交付物/状态三选一）？
- [ ] 结果可验证（老板能去查到这个数字/看到这个交付物）？
- [ ] 没写"基本完成""有所推进"这类空洞词？
- [ ] 一句话能读完（超 3 行就拆成两条）？
- [ ] 最重要的事项排在最前？

## 6. 排序规则

"本周完成"不是按时间排序，是按**重要性**排序：
1. 对业务结果影响最大的先写（上线、收入、核心指标）。
2. 其次是里程碑（评审通过、联调通过）。
3. 最后是日常（bug 修复、文档、支持）。

老板只看前 3 条的概率是 80%——把最重要的放前面，不是礼貌，是策略。

## 7. 改写实战：三组前后对比

**组 1：过程→结果**
```
改写前：这周在跟进支付改造项目
改写后：完成支付链路幂等改造并通过联调，预计周三上线
（追问挖出的：阶段到了联调通过，结果是"预计周三上线"）
```

**组 2：模糊→量化**
```
改写前：修复了一些线上 bug
改写后：修复线上 bug 8 个，其中 P1 级 2 个，crash 率从 0.5% 降到 0.3%
（"一些"→8 个；加分级；加结果指标变化）
```

**组 3：被动→主动**
```
改写前：参加了需求评审会
改写后：主导 3 个需求的评审：2 个通过进入开发，1 个打回补充方案，
       输出评审纪要并同步相关方
（"参加"→"主导"；结果是评审结论+纪要交付）
```

**改写手感**：每改一条，问自己"老板看了这条，能转发给他的老板吗"——能，就是合格的事项；不能，继续加结果。

## 8. 反模式

- ❌ "参与了 xx 项目"（参与了=没说你干了什么）
- ❌ "继续推进 xx"（推进到哪了？没结果就是没写）
- ❌ "基本完成 xx"（基本=没完成，VAG-001 会抓）
- ❌ 一条事项 5 行流水账（S/T/A/R 全展开，周报不是述职报告）
- ❌ 把"开会""学习"当主要事项（除非会议本身就是交付，如评审会输出了结论）

## 9. 常见问题

- **Q：这周真的没什么结果，都是过程，怎么办？** A：把"过程的阶段性结果"写出来："完成联调"就是结果，"输出评审纪要"就是交付物。真的一点阶段性成果都没有，诚实写并说明卡点（进"问题与风险"）。
- **Q：结果是别人的功劳，我只是配合？** A：写你配合的部分和它的结果："配合测试完成联调，阻塞问题清零"。不抢功，也不把自己写没。
- **Q：一条事项横跨两周，上周写过这周还写吗？** A：写，但只写"本周的新进展"。上周写"启动改造"，这周写"完成改造并上线"。不许复制粘贴。
- **Q：数字不好看还写吗？** A：写。数字不好看+根因+对策，比藏着强（见 lhg-wr-issue）。
- **Q：S/T 背景老板都知道，还写吗？** A：括号备注法：正文只写 A+R，S/T 放括号里备查。老板不问不展开。
- **Q：事项太多，超过 8 条？** A：合并同类项（"修复 bug 8 个"合并成 1 条），或把次要的降级为一句话。超过 8 条的"本周完成"没人看完。

- **Q：事项的结果要写"同比/环比"吗？** A："本周完成"里写绝对结果（"成功率 99.1%"），对比放"关键数据"里。四段分工：完成讲"做成了什么"，数据讲"变得怎么样"。
- **Q：结果动词用腻了，每条都是"完成"？** A：换：交付（给出去的东西）、上线（发布的系统）、修复（bug）、提升/降低（指标变化）、通过（评审/验收）、落地（方案变成现实）。动词越具体，事项越可信。
- **Q：一条事项里有两个结果？** A：拆成两条，或只写最重要的那个。"完成 A 上线，B 的评审也通过了"→拆成两条。贪多等于没重点。
## 10. 自检与反馈

**质检门**：
- [] 每条都有结果（数字/交付物/状态）？
- [] 无空洞表述？
- [] 按重要性排序，最重要的在前 3 条？
- [] 审计脚本 STAR-001/VAG-001 通过？

**标准冒烟用例**：取 3 条过程型原始记录（如"在做 xx""跟进 xx"），用追问法改写成 STAR 事项，对照第 5 步质检表自查。

**发现问题**：到本仓库提 issue（标题前缀 `[lhg-wr-star]`），描述：场景、原始记录样例（脱敏）、期望行为。
